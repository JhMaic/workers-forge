# monorepo-opennext

A fully runnable pnpm monorepo demonstrating workers-forge + the **latest** `@opennextjs/cloudflare` + **latest Next.js**.

- **`packages/workers`** — a Worker that owns a KV namespace and exposes `get/set/list` over typed RPC.
- **`packages/web`** — a Next.js **16** app deployed via `@opennextjs/cloudflare`. Reads/writes KV **only through the worker's RPC** — never holds its own KV binding.

The web package has two simple pages backed by the worker:

- **`/set`** — a form that writes a key/value pair via the worker's `set(key, value)` RPC (uses a React Server Action).
- **`/read`** — looks up a value by key via the worker's `get(key)` RPC, and lists all stored keys via `list()`.

Both packages share **one** root-level `workers-forge.config.ts` (prefix + envs), which is what makes the `services[].service` name composed by the web package (`${envs.prefix}kv-store${envs.suffix}`) match the actual deployed name of the worker.

## Cross-package wiring

1. `packages/workers/src/modules/kv-store/index.ts` declares a Worker named `kv-store` with a KV binding. Its actual deployed name is `${prefix}kv-store${suffix}` — e.g. `mre-kv-store-local`.
2. The same file exports `type KvStoreRpc = WorkerRPC<typeof worker>`; `packages/workers/index.ts` re-exports it.
3. `packages/web/src/app.meta.ts` imports `KvStoreRpc` and writes:
   ```ts
   services: {
     KV_STORE: service<KvStoreRpc>(`${envs.prefix}kv-store${envs.suffix}`),
   }
   ```
   `envs.prefix` / `envs.suffix` are seeded at build time from the **same** shared config, so the resolved string equals the workers package's deployed name in every env.
4. `packages/web/src/cloudflare-env.d.ts` uses `declare global { interface CloudflareEnv extends AppEnv {} }` to merge the binding types into OpenNext's `CloudflareEnv`. After this, `getCloudflareContext().env.KV_STORE` is typed as `ServiceStub<KvStoreRpc>` with `.get()` / `.set()` / `.list()` available.

## Running locally

Two terminals (or use `concurrently` via the root `dev:local` script):

```sh
# Terminal A — workers package: spawns `wrangler dev` for kv-store
pnpm -F @example/workers dev:local

# Terminal B — web package: generates wrangler.jsonc, starts `next dev`
pnpm -F @example/web dev:local
```

Or one command:

```sh
pnpm dev:local   # uses concurrently to run both
```

Then open **http://localhost:3000**:

1. Click **/set**, enter a key and value, click "Save". You'll be redirected to `/read?key=<your-key>`.
2. The `/read` page shows the value (fetched via the worker's `get()` RPC) and lists all keys (via `list()`).

The data path is:
```
browser → /set Server Action → getCloudflareContext().env.KV_STORE.set(key, value)
       → wrangler dev registry → kv-store worker → env.KV.put(key, value)

browser → /read?key=X        → getCloudflareContext().env.KV_STORE.get(key)
       → wrangler dev registry → kv-store worker → env.KV.get(key)
```

This works because both `wrangler dev` (workers package) and `initOpenNextCloudflareForDev` (web package, via `next.config.mjs`) share **the same `.wrangler/state` directory** (resolved relative to each package, but both pointing at `monorepo-opennext/.wrangler/state`). The wrangler dev registry uses this to route service-binding calls.

## How `workers-forge gen` fits in

`gen` is the new subcommand added specifically so single-app projects (Next.js / Remix / etc.) can leverage workers-forge's env mechanism without paying for the multi-worker `build/dev/deploy` machinery:

```sh
workers-forge gen <metaFile> --out <path> [--env <name>] [--config <path>]
```

- `<metaFile>`: a TS file that named-exports `meta` (authored with `defineWorkerMeta` for type safety)
- `--out`: target `wrangler.jsonc` path (default: `./wrangler.jsonc`)
- `--env`: activates a named entry from `envs[]`; overlays vars, suffixes the name, injects `CF_CONFIG_*` into `process.env` before importing the meta
- `--config`: path to `workers-forge.config.ts` (optional — only `envs[]`, `baseConfig`, `prefix` are consulted; `modules` / `dev` are ignored by `gen`)

In this example the web package calls `gen` from npm scripts (see `packages/web/package.json`).

## Per-env config

`envs[].envFile` accepts an **array** of dotenv files, layered in order (later entries override earlier). The root config does:

```ts
envs: [
  { name: 'local',      envFile: ['.env', '.env.local'],      suffix: '-local' },
  { name: 'staging',    envFile: ['.env', '.env.staging'],    suffix: '-staging' },
  { name: 'production', envFile: ['.env', '.env.production'], suffix: '' },
]
```

so `APP_NAME` from `.env` is shared, while `LOG_LEVEL` and `CF_CONFIG_KV_ID` are overridden per env.

## Deploy

Order matters — workers must exist before the web package's service binding can route to them. Edit `.env.staging` / `.env.production` with real Cloudflare resource IDs first, then:

```sh
pnpm deploy:staging
pnpm deploy:production
```

The root `deploy:*` scripts chain workers first, then web:

```
pnpm -F @example/workers deploy:staging   # workers-forge deploy --build --env staging
&& pnpm -F @example/web   deploy:staging  # workers-forge gen --env staging && opennextjs-cloudflare deploy
```

## Known quirks

- **Webpack/Turbopack cache in `.next/`** — if you change `src/app.meta.ts` significantly and see stale build errors, `rm -rf packages/web/.next` and restart.
- **TypeScript IDE errors on `workers-forge.config.ts`**: ensure your IDE picks up `monorepo-opennext/tsconfig.json` (which uses `moduleResolution: "Bundler"` to honor the `./build` subpath export). Most IDEs find this automatically; if not, restart the TS server.
- **Older Node**: if you must stay on Node 20, pin `wrangler` to `~4.85.0` and `@opennextjs/cloudflare` to `~1.18.1`. The current pins target Node 22+.
