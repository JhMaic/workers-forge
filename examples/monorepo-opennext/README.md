# monorepo-opennext example

A minimal pnpm monorepo where:

- `packages/workers` — declares one or more Workers via `workers-forge` (here: a single `kv-store` Worker that owns a KV namespace and exposes RPC methods).
- `packages/web` — a Next.js app deployed via `@opennextjs/cloudflare`. Reaches the KV **only** through the `kv-store` Worker's typed RPC; never holds a direct KV binding.

Both packages share **one** `workers-forge.config.ts` at the monorepo root, which carries the `prefix` and `envs[]` arrays — that's what guarantees cross-package sibling names (`${prefix}kv-store${suffix}`) line up in every environment.

```
monorepo-opennext/
├── workers-forge.config.ts      # ← shared by both packages
├── .env / .env.local / .env.staging / .env.production
└── packages/
    ├── workers/
    │   ├── src/modules/kv-store/index.ts   # defineWorker + KV binding + RPC methods
    │   └── index.ts                        # type-only barrel exporting KvStoreRpc
    └── web/
        ├── src/app.meta.ts                 # defineWorkerMeta + service<KvStoreRpc>(…)
        ├── src/cloudflare-env.d.ts         # CloudflareEnv extends AppEnv
        ├── src/api-handler.ts              # demo route reading env.KV_STORE
        └── wrangler.jsonc                  # generated by `workers-forge gen`
```

## How the cross-package wiring works

1. `packages/workers/src/modules/kv-store/index.ts` declares a Worker named `kv-store`. Its deployed name will be `${prefix}kv-store${suffix}` — e.g. `mre-kv-store-staging`.
2. `packages/workers/index.ts` re-exports `type KvStoreRpc = WorkerRPC<typeof worker>`.
3. `packages/web/src/app.meta.ts` imports `KvStoreRpc` and writes:
   ```ts
   services: {
     KV_STORE: service<KvStoreRpc>(`${envs.prefix}kv-store${envs.suffix}`),
   }
   ```
   `envs.prefix` / `envs.suffix` are seeded at build time from the **same shared config**, so the resolved `service` string equals the workers package's actual deployed name.
4. `packages/web/src/cloudflare-env.d.ts` augments `CloudflareEnv` with `InferEnv<typeof meta>`, so `getCloudflareContext().env.KV_STORE` becomes typed as `ServiceStub<KvStoreRpc>` with `.get()` / `.set()` / `.list()` available.

## CLI

All scripts at the root level:

```sh
pnpm install

# Local dev — runs workers + web in parallel; Next.js connects to workers via the
# wrangler dev registry (same persistTo path keeps KV state shared).
pnpm dev:local

# Staging dev (workers in staging mode + Next.js with staging wrangler.jsonc)
pnpm dev:staging

# Deploy
pnpm deploy:staging
pnpm deploy:production
```

Or per-package:

```sh
# Workers package (uses the existing workers-forge commands unchanged)
pnpm -F @example/workers dev:local
pnpm -F @example/workers deploy:staging

# Web package (uses the new `workers-forge gen` subcommand)
pnpm -F @example/web gen:staging      # writes packages/web/wrangler.jsonc
pnpm -F @example/web dev:staging      # gen + `next dev`
pnpm -F @example/web deploy:staging   # gen + `opennextjs-cloudflare deploy`
```

`workers-forge gen` is **the only new command** introduced for OpenNext support. It takes:

```sh
workers-forge gen <metaFile> --out <path> [--env <name>] [--config <path>]
```

The metaFile must named-export a `meta` object (created with `defineWorkerMeta` for typed authoring). Reusing the project's `workers-forge.config.ts` is optional — only `envs[]`, `baseConfig`, and `prefix` are consulted by `gen`; `modules` / `dev.ports` etc. are ignored.

## Local dev: keeping KV state shared between workers and Next.js

The shared config sets `dev.persistTo: '.wrangler/state'`. This is automatically picked up by `workers-forge dev` for the workers package. For Next.js to see the same KV state, point `@opennextjs/cloudflare`'s dev integration at the same path — usually by reading `dev.persistTo` from the shared config in your `next.config.js`:

```js
// packages/web/next.config.js (you'd add this when wiring up a real Next.js app)
import { initOpenNextCloudflareForDev } from '@opennextjs/cloudflare';
import cfg from '../../workers-forge.config';

await initOpenNextCloudflareForDev({
  persist: { path: `../../${cfg.dev.persistTo}` },
});

export default { /* your next config */ };
```

The wrangler dev registry handles the service-binding RPC routing automatically — no further glue code needed.

## Production deployment

`.env.staging` and `.env.production` carry real Cloudflare resource IDs (`CF_CONFIG_KV_ID=…`). `workers-forge` injects these into `process.env` *before* importing your meta files, so `process.env.CF_CONFIG_KV_ID!` in `kv-store/index.ts` resolves to the right value per env.

Deploy in order:

```sh
pnpm deploy:staging       # workers first (so the kv-store name exists), then web
```

The root script chains them: `pnpm -F @example/workers deploy:staging && pnpm -F @example/web deploy:staging`.

## What's deliberately omitted

This example focuses on the **workers-forge integration**, not on building a complete Next.js app. To make the web package actually runnable as Next.js you'd add `next`, `react`, `react-dom`, and `@opennextjs/cloudflare` (see `_realDependencies` in `packages/web/package.json` for versions). The workers-forge contract — `gen` produces a correct `wrangler.jsonc`, types flow from `defineWorkerMeta` through `InferEnv` to `CloudflareEnv` — is fully exercised as-is.
